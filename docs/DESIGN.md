# Signature 设计说明与实验日志

这一篇记录 `signature` 预设是怎么来的，**包括被否决的路径和没有达成的目标**。它是一个可复现的工程设计日志，不是一份宣称「已完成逐字重绘」的宣传稿。仓库不含字体二进制，所有结论都可由 `scripts/measure_dna.py`、`scripts/harmonize.py` 与 `assets/harmony-report.json` 复算。

## 1. 要解决的是什么

`cjk` / `cjk-bold` / `multilingual` / `full` 四档都直接使用思源宋体（Noto Serif CJK SC）的中文轮廓，只做覆盖与字重变化。把中文和 Anthropic Serif Web Text 排在同一行时，两者属于两套衬线语法：

- 西文是 **bracketed 平板衬线**：`I` 的顶部衬线头宽 299px，主干 107px，在 14% 字高内用圆滑 bracket 收回主干；
- 中文横画末端是**上翘的三角顿笔**，横画 29px、竖笔 83px，横竖对比 2.862，明显高于西文 `H` 的 107/51 = 2.098。

目标是让中文按西文的轴线、字怀与衬线尺度重新生成，而不是「把 Noto 换个名字」。

## 2. 测量方法

`scripts/measure_dna.py` 在固定 1000 px em 下用 FreeType 光栅化，量取：

| 对象 | 量法 | 结果 |
| --- | --- | --- |
| `H` 竖干 / 横干 | 横干上方 30% 字高处取两段竖干；中线竖直扫描取横干 | 107 / 51 px，对比 **2.098** |
| `I` 衬线 bracket | 从衬线头到主干逐行取最大宽度 | 299 → 221 → 152 → 127 → 109 → 107，头/干 **2.794**，14% 字高收窄 |
| `O` 应力轴 | 180° 内每 5° 沿径向取最长墨段 | 最细轴 85°（偏离垂直 **5°**），对比 2.322 |
| `x` 与 `H` 包围盒 | x-height / cap-height | 0.540 / 0.720 em，比值 **0.75** |
| `n` 主干 / 字身 | 中间行取两段主干 | 0.171 |
| 「中」「二」 | 中间行竖笔、中线横画 | 83 / 29 px，对比 **2.862** |

全部数值写入 `assets/design-dna.json`。`scripts/harmonize.py` **只从该文件读参数**，没有硬编码的设计值。

## 3. 三个被实测推翻的直觉

**一、「中文对比过高，西文压低了对比」只说对一半。** 两者确实差 36.4%，但 `O` 的曲线对比是 2.322，和 `H` 的 2.098 不同；真正稳定可比的基准是 `H` 的横干/竖干。中文横画相对太细，不是「整体太粗」。

**二、「换更粗的字重能压低对比」完全相反。** 思源宋体加粗时几乎不加横画，只加竖笔：

| 字重 | 横画 px | 竖笔 px | 对比 |
| --- | --- | --- | --- |
| ExtraLight | 30.0 | 42.5 | 1.417 |
| Light | 30.0 | 52.5 | 1.750 |
| Regular | 27.5 | 67.5 | **2.455** |
| Medium | 30.0 | 85.0 | 2.833 |
| SemiBold | 30.0 | 97.5 | 3.250 |
| Bold | 27.5 | 122.5 | 4.455 |
| Heavy | 27.5 | 155.0 | 5.636 |

所以 `cjk-bold` 解决的是「墨色淡」，不是「风格不搭」；它把对比推到 4.455，离西文更远。

**三、「总有一档字重精确匹配 2.098」不成立。** 最接近的是 Light（1.750）与 Regular（2.455），分别差 0.348 与 0.357。七档里没有中间值。

## 4. 最终采用的三项处理

### 4.1 源字重改为 Regular（对比度对齐）

`signature` 预设把 `--cjk-ttc` 指向 `NotoSerifCJK-Regular.ttc`（wght 400），而不是其余四档的 Medium。它是不过分清瘦的前提下对比最接近西文的一档。生成字体实测：

| | `cjk` (Medium) | `signature` (Regular + 重绘) |
| --- | --- | --- |
| 横画 / 竖笔 | 30.0 / 82.5 px | 27.5 / 62.5 px |
| 横竖对比 | 2.750 | **2.273** |
| 西文目标 | 2.098 | 2.098 |
| 同段墨色 | 21,178 px | 18,313 px |

代价如实说明：墨色降约 **13.5%**，整体比 `cjk` 清瘦。若嫌淡，应改用 `cjk-bold`，而不是给 `signature` 叠加 `font-weight: 700`（那会合成加粗西文）。

### 4.2 末端竖直平切（衬线语法重建）

`scripts/harmonize.py` 在 2000 UPM 的二次曲线轮廓上，把外轮廓中「x 方向极值 + 转角足够锐」的横画末端尖角，替换为三个点：上端点、一个向内凹的 off-curve bracket 控制点、下端点。末端 x 严格不变，只在 y 上下展开；展开量按实测的 `I` 衬线头/主干比 2.794 × 目标横画厚度，再乘 0.45 的汉字字面密度适配系数，得到 **99.5 units** 的衬线头。

刻意**不做水平外延**：汉字字面框没有余量，外延会让内轮廓产生脱离主体的细线。

### 4.3 应力轴对齐

按 `O` 实测的 5° 偏离，对全部中文轮廓点施加 0.035 的轻微剪切（取 40% 强度，避免整字歪斜）。2000 UPM、全宽 1em、基线、hhea 1985/-515、19 个 GSUB、2 个 GPOS 全部不动；**720 个西文字形逐字节不变**。

## 5. 被否决的路径（可复现）

工程过程中试过并明确放弃的做法，记录在此以免后来者重复踩坑：

| 做法 | 结果 | 原因 |
| --- | --- | --- |
| 逐点沿「相对轮廓中心」法向推近水平边以加粗横画 | 大字号 `raster overflow` | 同一条长水平边的两端得到相反法向（一端 +10、一端 −8 units），边被扭成自交斜线，FreeType 扫描转换在 ≥800 px 溢出 |
| 改按轮廓绕向统一法向 | 横画被压细，对比变 8.0 | cu2qu 输出的轮廓绕向与 TrueType 常规约定相反，法向整体指反 |
| 衬线沿斜法向展开 | 复杂字冒出细碎飞线 | 「下端点」跑到后续轮廓点左侧，形成回折尖刺 |
| 允许内轮廓参与端点重建 | 平均每字 17.8 个端点，噪声大 | 折笔拐角被误判为横画末端 |
| 用 `TTGlyphPen` 规范化轮廓结构 | 溢出依旧 | 确认问题是几何而非 `flags` 结构 |
| 端点判定用「尖角 cos < 0.40」 | 「一」「二」三角顿笔没被替换 | 实测楔形尖端转角 59°（cos 0.51），左端外法向 |ny| 仅 0.30，阈值收紧过头 |

最终把加粗整体关闭（`edge_delta_units = 0`），仅保留剪切与末端平切。分组件验证显示这两项在 400/800/1000 px 全部通过。

## 6. 一致性怎么保证

这是「三万多字一致性」这一难点的工程回答：**不是逐字设计，而是逐字同参**。

- 所有阈值、位移、衬线头尺寸由同一份 `design-dna.json` 计算，全字符集共用一套参数；
- 只在外轮廓、且每轮廓最多 2 个、每字最多 6 个末端动手；点数超过 400 的复杂字只做剪切；
- 变换后强制校验 `coordinates` 与 `flags` 等长、重算 `recalcBounds`；
- 每个字的处理结果写进 `assets/harmony-report.json`，覆盖率与失败数可被第三方复算。

最终报告：31,004 个字中 **30,925 个完成重建（99.75%）**，2 个超大字直通、77 个无可用末端、0 失败；共 **221,484 个衬线端**（7.14/字），轮廓点数 +8.5%。抽 10 个常用字在 400/800/1000/1400 px 四个字号渲染，全部通过，无溢出。

## 7. 没有达成的部分（重要）

必须说清楚：这一版是**设计 DNA 驱动的参数化重绘**，不是设计师逐字手绘的 L3 完全体。

- **三角顿笔的斜坡没有被完全消除。** 宋体横画末端由一整串斜向控制点构成，把尖端一个点削平只能得到方头，斜坡仍在，样张的「一」「二」放大区可以直接看出来。彻底替换需要笔画骨架数据（区分横、竖、撇、捺、折）与分类规则，现有轮廓里没有这些信息。
- **对比度停在 2.273，没有到 2.098。** 七档字重没有精确匹配，逐点轮廓加粗又会破坏渲染稳定性。
- **字怀 / 轴线 / 中宫未逐字调整。** 只做了全局 5° 应力剪切，没有按西文字怀开放度重设每个字的内白。
- **没有人工抽检。** 31,004 字全部由同一套规则处理，未做逐字目检；生僻字与扩展区字形可能存在个别不理想的处理。

如果要把这些做完，需要：汉字笔画/部件分解数据、按笔段类型分类的端点重建规则、对通用规范汉字 8105 字的人工抽检回路，以及对复杂字的独立降级策略。那是真正以月计的字体设计工程，不是一次脚本运行。
